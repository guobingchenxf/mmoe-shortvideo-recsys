## 1. 项目定位

### 1.1 这个项目要证明什么

面试作品的价值不在于"用了多新的模型"，而在于**证明你理解工业推荐系统的真实约束**。因此本项目的核心是两件事：

- **多目标优化**：短视频不是"点不点"的二分类问题。平台同时关心点击率、点赞率、完播时长，
  而这些目标相关但不同（标题党能拉高点击却压低完播）。如何用**一个模型**同时建模，是核心命题。
- **工程落地**：从离线特征到在线服务，链路完整且可运行。包含防特征泄漏、低延时推理、
  冷启动处理这些只有真做过才会遇到的问题。

### 1.2 覆盖的技术点

| 层次 | 技术点 |
|---|---|
| 数据 | 隐因子模型、截距校准、标签相关性注入 |
| 特征 | 声明式特征管理、稳定哈希、周期性编码、序列特征、防泄漏 |
| 模型 | MMoE、Uncertainty Weighting、多任务损失、稀疏 Embedding |
| 训练 | SparseAdam + Adam 双优化器、EarlyStopping、GAUC |
| 服务 | FastAPI、多路召回、批量推理、预热、缓存抽象、延时统计 |
| 部署 | Docker、docker-compose、健康检查 |

## 2. 问题建模：为什么是这三个目标

### 2.1 三个目标的关系

设用户 u 与视频 v，我们同时预测：

| 目标 | 类型 | 业务含义 | 训练损失 |
|---|---|---|---|
| click | 二分类 | 是否有效点击 | BCE |
| like | 二分类 | 是否点赞 | BCE |
| watch_time_ratio | 回归 | 完播率 ∈ [0,1] | MSE |

三者的关系是**相关但不同**：

- **正相关部分**：用户兴趣匹配度高 → 更可能点击、更可能看完、更可能点赞。这部分适合共享底层；
- **冲突部分**：猎奇标题能骗到点击，但完播率低、也不会被点赞。这部分需要任务各自独立的表达。

这正是多任务学习（以及 MMoE）存在的理由：**共享能利用相关性，独立能缓解冲突**。

### 2.2 一个直接的问题：为什么不用三个独立模型

可以，但代价是：

1. 参数与推理成本 ×3（线上要维护 3 个模型）；
2. 稀疏目标（点赞率仅 1%）学不好 —— 点赞样本只有 3000 条，
   独立模型无法借助点击信号来辅助学习；
3. 线上打分要跑 3 次前向，延时翻倍。

而 MMoE 用**一次前向**产出三个目标的分数，这是工程上的直接收益。

## 3. 数据是怎么造的

真实数据集（如 Kuaishou）不易获取，且不一定含完播率标签，因此本项目用**隐因子模型**生成数据。
关键在于：**不能随机造标签**，否则多任务学习就失去了意义（没有可学的结构）。

### 3.1 生成流程

```
1. 用户隐兴趣矩阵 U ∈ R^{n_users × K}    ~ Dirichlet(0.3)，稀疏偏好
2. 视频隐主题矩阵 V ∈ R^{n_videos × K}   ~ Dirichlet(0.3)
3. 曝光对采样：视频曝光概率 ∝ 热度（对数正态），复现"头部效应"
4. 相关性 r = <U[user], V[video]>，再标准化为 r_z
5. 点击 logit  = 1.6·r_z + 0.6·pop_z      → 截距校准到 5%
6. 完播率均值  = clip(0.12 + 0.55·σ(1.1·r_z + 0.25·pop_z))
   完播率      ~ Beta(mean·c, (1-mean)·c)，c = 2.0  → 长尾
7. 点赞 logit  = 1.2·r_z + 1.0·watch_z + 0.3·pop_z → 截距校准到 1%
   点赞        = click ∧ Bernoulli(p)
```

这里有两个设计要点：

**① 点击与完播都依赖 r_z，但点击还额外依赖热度。** 这让两个目标共享主要信号又不完全一致。

**② 点赞的 logit 里显式加入了 `watch_z`（完播率的标准化值）。** 这条依赖关系是多任务学习价值的来源：
如果点赞与完播完全独立，那三个任务就没有可共享的结构了。

### 3.2 截距校准：为什么必须做

sigmoid 输出的均值由 logit 的分布决定，随手设一个截距很难精确命中"5%"这种目标。
本项目用**二分法**求截距 b，使 `mean(σ(logits + b)) = target`：

```python
def calibrate_intercept(logits, target_rate, weights=None, ...):
    lo, hi = -30.0, 30.0
    for _ in range(max_iter):
        mid = (lo + hi) / 2
        p = sigmoid(logits + mid)
        rate = p.mean() if weights is None else (weights * p).mean()
        if abs(rate - target_rate) < tol: return mid
        lo, hi = (mid, hi) if rate < target_rate else (lo, mid)
    return (lo + hi) / 2
```

`weights` 参数用于处理"点赞必须以点击为前提"：传入 click 向量后，
校准目标变成"全曝光口径下的点赞率"。

**实测结果**：目标 CTR 0.05 → 实际 0.0501；目标点赞率 0.01 → 实际 0.0100。

### 3.3 数据规模的坑（重要）

最初用 12 万条曝光训练，模型**第 1 个 epoch 就达到最优**，之后验证指标持续下滑。
根因是**交互稀疏度**：

```
密度 = 300,000 / (5000 × 20000) = 0.03%
```

在 5000×20000 的 ID 空间上，每个视频平均只有 15 次曝光，矩阵分解类模型无法恢复隐因子。
把数据扩到 30 万条后，click AUC 从 0.593 提升到 0.625，但"epoch 1 最优"的模式依然存在。

**这不是 bug，而是稀疏推荐的固有难题。** 工业界的解法是：更密的交互（用户量级 × 曝光量级）、
负采样控制正负比、以及对 ID 类特征做强正则（dropout / 降低维度 / 哈希碰撞容忍）。

## 4. MMoE 论文精读与实现对照

论文：Ma et al., *Modeling Task Relationships in Multi-task Learning with
Multi-gate Mixture-of-Experts*, KDD 2018。

### 4.1 论文要解决的问题

多任务学习的两种极端：

- **硬共享（Shared-Bottom）**：所有任务共用一个底层。
  当任务相关性低时，共享底层被拉向"平均解"，每个任务都受损 —— 称为 **negative transfer**。
- **完全独立**：无法利用任务间的共享知识，稀疏任务学不好。

论文用实验说明：**任务相关性越低，硬共享的负迁移越严重**，并提出 MMoE 作为折中方案。

### 4.2 MMoE 的结构

```
                    ┌──── Expert_1 ────┐
    x ──► Shared ──► ├──── Expert_2 ────┤
          Bottom     │       ...        │
                    └──── Expert_N ────┘
                            │  每个专家输出 H 维
       Gate_1 ─► softmax ─► 加权求和 ─► Tower_1 ─► ŷ₁ (CTR)
       Gate_2 ─► softmax ─► 加权求和 ─► Tower_2 ─► ŷ₂ (Like)
       Gate_3 ─► softmax ─► 加权求和 ─► Tower_3 ─► ŷ₃ (完播率)
```

数学表达：

```
h          = SharedBottom(x)                        # 共享表示
E_i        = Expert_i(h),          i = 1..N         # N 个专家
g^k        = softmax(W_g^k · h)                     # 第 k 个任务的门控权重
f_k(x)     = Tower_k( Σ_i g^k_i · E_i )             # 门控加权融合后再过塔
```

**关键理解**：门控的输入是共享表示 h（与专家相同），输出是 N 维 softmax 权重。
它相当于让每个任务"自己决定该听哪些专家的意见"。

### 4.3 关于 Shared Bottom 的一处澄清

原论文的 MMoE **并没有**在专家之前额外加一层 Shared Bottom —— 可以认为"专家集合本身"
就是共享底层。但很多工业实现会在专家之前插一个共享 MLP 做维度压缩与特征预融合。

本项目把它做成可配置项（`shared_bottom_hidden`）：

- 非空（默认 `[256]`）：输入 → SharedBottom → Experts → Gates → Towers
- 空列表：退化为论文原始结构（专家直接作用于输入）

代码位置：`recsys/models/mmoe.py` 的 `MMoE.__init__`。

### 4.4 实现中最容易写错的地方

**① 门控权重的融合方式**。必须对"专家输出"做加权求和，而不是对"专家权重"求和：

```python
expert_outs = torch.stack([e(h) for e in self.experts], dim=1)   # (B, E, H)
g = gate(h)                                                       # (B, E)
fused = torch.bmm(g.unsqueeze(1), expert_outs).squeeze(1)          # (B, H)
```

**② 门控必须 softmax 归一化**，否则不同样本的门控输出尺度不一致，训练不稳定。
本项目有单测 `test_gate_weights_sum_to_one` 守住这一点。

**③ 单专家退化即 Shared-Bottom**。当 `num_experts=1` 时，softmax 输出恒为 1，
模型等价于"共享底层 + 多塔"—— 这正是论文的对照基线。本项目复用了这个性质实现 ablation，
省了一整套代码。

## 5. Uncertainty Weighting 推导

来源：Kendall et al., *Multi-Task Learning Using Uncertainty to Weigh Losses*, CVPR 2018。

### 5.1 问题：手工权重难调

最朴素的多任务损失是 `L = Σ w_t · L_t`，但：

- 各任务量纲差异大（BCE ≈ 0.2，MSE 可能只有 0.05），梯度量级差一个数量级；
- 结果往往是"某个任务主导训练"，其余任务学不动；
- `w_t` 需要反复人工试。

### 5.2 从不确定性出发的推导

把每个任务的观测噪声建模为高斯，其方差为 σ_t²，则最大化似然等价于最小化：

```
L = Σ_t [ 1/(2σ_t²) · L_t + log σ_t ]
```

直觉非常清晰：

- σ_t 大（任务噪声大、难学）→ `1/(2σ_t²)` 小 → **自动降低该任务权重**；
- `log σ_t` 是正则项，防止模型把所有 σ_t 推到无穷大（导致权重全归零）。

它本质上是**基于不确定性的梯度归一化**。

### 5.3 工程实现

直接学 σ_t 数值不稳定（σ 必须为正），因此令 `s_t = log σ_t²`：

```
L = Σ_t [ exp(-s_t) · L_t + 0.5 · s_t ]
```

`s_t` 初始化为 0 时 `exp(0)=1`，等价于"各任务等权"起步，训练中自动分化。

```python
# recsys/models/loss.py
total = total + torch.exp(-s) * loss_t + 0.5 * s
```

**注意**：原论文对回归任务是 `1/(2σ²)`、分类任务是 `1/σ²`；
工程上普遍采用上面这种统一系数的简化写法，本项目亦如此（在代码注释中已说明）。

### 5.4 一个观察

训练日志里能看到任务权重从 1.0 缓慢增长到 1.7~1.8：

```
[epoch 1] 任务权重={'click': 1.101, 'like': 1.117, 'watch_time_ratio': 1.127}
[epoch 4] 任务权重={'click': 1.536, 'like': 1.596, 'watch_time_ratio': 1.589}
```

这是**符合理论预期的**：最优解满足 `exp(-s_t) = 0.5 / L_t`，
当 BCE 损失收敛到 0.2~0.3 时，权重应趋向 `0.5/0.25 ≈ 2.0`。

**但这同时说明一个副作用**：随着权重增大，整体损失尺度变大，等效学习率被放大，
后期训练会变得不稳定。这也是本项目最终**收敛很快、容易过拟合**的原因之一
（关掉 Uncertainty Weighting 后曲线形态一致，说明它不是主因，但确实有放大作用）。

生产环境的常见做法是给 `s_t` 加 clamp（如限制在 `[-3, 3]`）来避免权重无限增长。

## 6. 特征工程详解

### 6.1 声明式特征管理

```
FeatureSchema
├── dense      : 连续值 -> 归一化后拼进 MLP
├── sparse     : 单值类别 -> 查 Embedding
├── multi_hot  : 多值类别 -> Embedding + masked-mean 池化
└── sequence   : 变长序列 -> padding + 池化
```

**为什么要单独抽象一层**：特征名散落在数据生成、离线特征、在线服务三处，写错一个字母
就是静默错误；更重要的是，**线上线下必须用同一份 spec 编码**，否则会出现
Training-Serving Skew —— 训练时特征 A、线上推理时特征 B，模型输入完全错位却不报错。

本项目的做法：训练时把 `FeatureSchema` + 归一化统计量一起存进模型 bundle，
服务启动时从同一个 bundle 读取，从机制上保证一致。

### 6.2 稳定哈希：一个真实的线上事故源头

**Python 的 `hash()` 对字符串带随机盐**（`PYTHONHASHSEED`），同一字符串在不同进程里
哈希值不同。如果离线训练跑在进程 A、线上服务跑在进程 B：

```
离线: hash("video_123") % 100000 = 41234
线上: hash("video_123") % 100000 = 87211   # 完全不同！
```

特征索引错位，模型输入"另一套特征"，但代码不会报错。这是最难排查的一类线上问题。

本项目统一使用 `blake2b` 做稳定哈希：

```python
digest = hashlib.blake2b(f"{seed}:{value}".encode("utf-8"), digest_size=8).digest()
return 1 + int.from_bytes(digest, "big") % (bucket_size - 1)
```

注意哈希结果从 **1** 开始 —— 0 号位保留给 multi_hot / sequence 的 PAD。
（单值 sparse 特征不需要 padding，索引 0 是合法取值。）

**哈希碰撞是固有代价**，本项目会输出诊断：

```
哈希碰撞诊断 [video_id]: 唯一值=19817, 唯一桶=17996, 碰撞率=9.19% (桶数=100000)
```

工业界的取舍：桶数越大碰撞越少，但稀疏参数越多、训练越慢 ——
通常配合更大的桶 + 稀疏更新（SparseAdam）来平衡。

### 6.3 三重防泄漏

这是特征工程里最容易被忽视、后果最严重的部分。**泄漏不会让程序崩溃，只会让离线指标虚高、上线掉点。**

| 泄漏类型 | 本项目做法 | 测试 |
|---|---|---|
| **标签泄漏** | 历史统计与行为序列严格"先记录、后更新"，只用当前样本之前的数据 | `test_user_sequence_has_no_future_leakage`、`test_history_stats_excludes_current_row` |
| **统计量泄漏** | 归一化 mean/std 只在训练集 fit，再 transform 验证集 | — |
| **时间泄漏** | 按时间切分 train/valid（前 80% / 后 20%），而非随机切分 | — |

行为序列构造的核心代码（`build_user_sequence`）：

```python
for i in order:            # 已按时间升序排列
    h = history[users[i]]
    if h:                  # 先写入当前行的序列（不含自己）
        recent = list(h)[::-1]     # 最新在前
        seq[i, : len(recent)] = recent
    if labels[i] == 1:     # 再把当前行加入队列，供后续行使用
        h.append(hash(items[i]))
```

顺序不能颠倒。反过来写就会把当前样本自己也放进序列里 —— 一个典型的标签泄漏。

### 6.4 周期性特征用 sin-cos 编码

小时（0~23）和星期（0~6）是环状量。直接用整数会让模型以为 23 点和 0 点"距离很远"，
而实际上它们是相邻的。用 sin-cos 编码保留环状邻近性：

```
hour_sin = sin(2π·hour/24),  hour_cos = cos(2π·hour/24)
```

### 6.5 多值特征与序列的池化

genres（视频标签）和 user_seq（用户历史点击）都是变长特征，需要：

1. **padding / 截断**到定长 `max_len`；
2. **masked mean 池化**：忽略 PAD 位置，避免被 0 向量稀释。

```python
mask = (ids != PAD_INDEX).float().unsqueeze(-1)
pooled = (emb * mask).sum(dim=1) / mask.sum(dim=1).clamp(min=1.0)
```

> 等效的高效写法是 `nn.EmbeddingBag(mode="mean", padding_idx=0)`，
> 但显式做 mask 更透明、更易验证，本项目采用后者。

## 7. 训练工程优化

### 7.1 定位瓶颈：优化器 step 占了近一半时间

最初的训练是 `0.634s/batch`，逐段计时后发现：

| 阶段 | 耗时 |
|---|---|
| forward | 0.147s |
| backward | 0.200s |
| **optimizer.step** | **0.287s** |

优化器为什么这么慢？因为 4 张 10 万级词表的 Embedding 共 **325 万参数**，
普通 Adam 每一步都要遍历整张表做动量更新，而实际被命中的行可能只有几千个。

### 7.2 双优化器方案

```python
# Embedding -> 稀疏梯度 + SparseAdam（只更新命中的行）
optimizers.append(torch.optim.SparseAdam(sparse_params, lr=cfg.model.embedding_lr))
# 其余参数 + 损失里的可学习任务权重 -> 普通 Adam
optimizers.append(torch.optim.Adam(rest + list(criterion.parameters()),
                                   lr=cfg.model.lr, weight_decay=cfg.model.weight_decay))
```

配套要点：

- `nn.Embedding(sparse=True)` 才会产生稀疏梯度；
- **不能混用**：PyTorch 的 Adam 不支持稀疏梯度，必须分开；
- SparseAdam 不支持 `weight_decay`；
- **Embedding 用独立学习率**（本项目 5e-3，是稠密层的 5 倍）——
  每个 id 一轮只被更新几次，同 lr 会导致学得太慢。

**效果**：单步 0.634s → 0.31s，提速约 2 倍。

### 7.3 GAUC 只在最后算一次

GAUC 需要按用户分组循环计算 AUC，开销大。训练过程中只算 AUC/RMSE 用于 EarlyStopping，
等选出最优模型后再完整评估一次（含 GAUC）。

### 7.4 指标实现要点

- **AUC** 用 Mann-Whitney U 统计量（秩和公式）实现，O(n log n)；
- **必须处理并列值**：对相同分数取平均秩，否则 AUC 会系统性偏移；
  实测全并列时结果为 0.5（有单测）；
- **GAUC** 只统计"组内同时含正负样本"的用户（否则 AUC 无定义），
  并以组内曝光数加权 —— 因为线上排序发生在同一用户的候选集内。

## 8. 实验分析：为什么 ablation 不显著

### 8.1 结果

| 任务 | 指标 | 单任务独立 ×3 | Shared-Bottom | MMoE(8 专家) |
|---|---|---|---|---|
| click | AUC | 0.6225 | 0.6219 | 0.6247 |
| click | GAUC | 0.5876 | 0.5912 | 0.5853 |
| like | AUC | 0.6675 | 0.6558 | 0.6657 |
| like | GAUC | 0.5590 | 0.5855 | 0.5756 |
| 完播率 | RMSE | 0.2975 | 0.2977 | 0.2968 |

### 8.2 统计上不显著

验证集 60,000 条、点击正样本 3019 个。AUC 的标准误约为：

```
SE(AUC) ≈ 0.005 ~ 0.008
```

而所有对比的差异都在 **±0.003** 以内 —— **全部落在噪声范围内**。
没有哪一方稳定胜出：MMoE 在 click/watch 上最好，单任务在 like 的 AUC 上最好，
Shared-Bottom 在两个 GAUC 上最好。

**不能宣称 MMoE 显著胜出。** 诚实地讲这个结论，比硬报一个假优势可信得多。

### 8.3 为什么没有差异：两个真实原因

**原因一：任务高度相关，硬共享本来就够用。**

本项目三个目标都由同一个隐因子 r 驱动。而 MMoE 原论文的核心结论恰恰是：
**任务相关性越低，MoE 相对 Shared-Bottom 的增益越大；任务高度相关时两者几乎等价。**
本实验正好落在论文预测的那一端 —— 结果与理论一致，而不是代码写错了。

**原因二：交互过于稀疏，三个模型撞到同一个天花板。**

30 万曝光铺在 5000×20000 的 ID 空间上，密度仅 0.024%。模型实际能稳定学到的
主要是"视频热度"这一个强特征（它作为 dense 特征直接给到了模型），
而真正需要从 ID 交互中学习的"隐相关性"学不出来。天花板相同，架构差异自然体现不出来。

### 8.4 两个仍然可靠的结论

1. **MMoE 用 1 个模型达到了 3 个独立模型的效果**（click+like 平均 AUC：0.6452 vs 0.6450），
   参数与工程量都更省 —— 这是多任务最实在的收益。
2. **Shared-Bottom 在 like 上出现负迁移**（0.6558 vs 单任务 0.6675，约 2 个标准误），
   MMoE 恢复到 0.6657。方向与论文"MoE 缓解负迁移"的结论一致。

### 8.5 要做出显著结论，应该怎么做

| 改进 | 说明 |
|---|---|
| **降低任务相关性** | 在数据里注入冲突目标（如"标题党"拉高点击但压低完播/点赞），任务冲突越强 MoE 越有优势 |
| **提高交互密度** | 曝光量提到百万级 / 收窄 ID 空间，让隐因子真正可学 |
| **多种子重复实验** | 每个配置跑 3~5 个随机种子取均值 ± 标准差，才能给出有统计意义的结论 |
| **控制参数量公平** | 当前 MMoE（3.63M）与单任务模型的 Embedding 预算相同，但稠密部分不同，可进一步对齐 |

## 9. 在线服务设计

### 9.1 漏斗链路

```
请求 → 取序列 → 多路召回(300) → 组装特征 → MMoE 打分 → 融合排序 → Top-K + 理由
```

**为什么不能对全库打分**：20000 个视频 × 每次前向的成本，延时无法接受。
漏斗式架构是必然选择。

### 9.2 多路召回

| 路由 | 说明 | 来源 |
|---|---|---|
| 同类目兴趣 | 用户最近点击过的类目下的视频 | 个性化最强 |
| 关注作者 | 用户互动过的作者的作品 | 强兴趣 |
| 热门推荐 | 全站热度 Top-N | 兜底 + 冷启动 |

按优先级顺序填充，同一视频只保留首次命中的来源（作为推荐理由的依据），
并过滤用户已经看过的视频。

> 生产环境会有更多路召回，核心一路是**向量召回**（双塔模型产出 user/item embedding，
> 用 Faiss / Milvus 做 ANN 检索）。

### 9.3 多目标融合

```python
SCORE_WEIGHTS = {"click": 0.6, "like": 0.3, "watch_time_ratio": 0.1}
fused = sum(SCORE_WEIGHTS[name] * pred[name] for name in pred)
```

这是业务上"综合体验"的定义。生产环境中这些权重通常由线上 A/B 实验或离线拟合确定，
而不是拍脑袋。

### 9.4 延时优化清单

| 手段 | 效果 |
|---|---|
| 模型预热（覆盖真实张量形状） | 避免首个请求承担 7s 的算子初始化开销 |
| 批量推理（一次前向算完 300 个候选） | 避免 300 次 Python 调用 |
| 特征批量编码 | 一次调用处理全部候选，比逐条快一个数量级 |
| 元数据转原生 dict | 把 `.loc` 查询变成 O(1) 哈希查找 |
| 线程数调优 | 见下节 |
| 召回候选量控制（500 → 300） | 推理耗时线性下降 |

## 10. 踩坑记录

### 坑 1：pip 读 requirements.txt 中文注释报错

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x80
```

pip 在 Windows 上用系统 locale（GBK）解码 requirements 文件。
**解法**：requirements.txt 全部使用 ASCII 注释（中文说明放到 README）。

### 坑 2：嵌入式数据与 pandas 版本冲突

全局 `numpy 2.2.3` 与 scipy / scikit-learn / pandas 的二进制接口不兼容，
`import pandas` 直接抛 `_ARRAY_API not found`。
**解法**：在项目 venv 内锁定 `numpy<2`（1.26.4），不动全局环境。

### 坑 3：线程超订让 P99 从 45ms 劣化到 1.4s

最初用 `TORCH_NUM_THREADS=4`，压测延时抖动到 6 秒。隔离测试结果：

| 线程数 | P50 | max |
|---|---|---|
| **1** | 44.6ms | **50.7ms** |
| 2 | 43.3ms | 317ms |
| 4 | 33.7ms | 308ms |
| 8 | 1416ms | 2112ms |

8 逻辑核上开 4/8 线程，小批量推理触发 OpenMP 线程超订 → 灾难性抖动。
**结论：推荐接口是"小批量 + 低延时"负载，限制为 1 线程反而更稳更快。**

### 坑 4：冷启动用户与越界上下文导致 500

`user_id=888888` 报 `IndexError: index out of range in self` ——
冷启动用户的 id 越过了用户 Embedding 词表（5000 行）。
客户端传 `device=999`、`source=-5` 同理。

**解法**：

- 冷启动用户映射到预留的合法槽位（生产环境应训一个 `<UNK>` 槽位）；
- 上下文特征在**接口边界**统一取模裁剪（只在系统边界校验，内部数据已保证合法）。

### 坑 5（附带）：pyarrow 与 pandas 的 list 列

multi_hot 与 sequence 存成 parquet 的 list 列时，需转换成 Python list（`row.tolist()`），
否则 pyarrow 类型推断可能不符合预期。

## 11. 生产化改造路线

按优先级排列：

1. **数据规模**：真实业务量级的交互数据（亿级曝光），这是效果的天花板。
2. **召回层**：双塔模型 + 向量检索引擎（Faiss / Milvus），替代规则召回。
3. **粗排层**：补齐"召回 → 粗排 → 精排 → 重排"链路，粗排用蒸馏的小模型。
4. **多任务进阶**：
   - `ESMM`：解决 CVR 样本选择偏差（本项目的 like 也依赖 click，同理可用）；
   - `PLE`（腾讯）：在 MMoE 基础上做"专家分层"，进一步缓解跷跷板效应；
   - `MMoE + 多目标融合的自动权重`（如 Pareto 优化）。
5. **序列建模**：把 masked-mean 池化升级为 `DIN`（注意力）/ `DIEN`（兴趣演化）/
   `Transformer4Rec`（长序列）。
6. **实时性**：Flink 实时特征 + 在线学习（增量更新），让模型跟上热点变化。
7. **工程**：
   - 特征平台（Flink + Redis / HBase），保证线上线下一致；
   - 模型服务化（Triton / TF Serving），支持多模型版本与热更新；
   - 全链路监控（延时、QPS、特征分布漂移告警）；
   - 分布式训练（参数服务器 / AllReduce）支撑十亿级样本。
8. **因果与偏差**：位置偏差纠正（PAL）、样本选择偏差（ESMM）、
   反事实推断（IPS）—— 让离线评估更接近线上真实效果。
